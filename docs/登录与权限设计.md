# 登录与权限功能设计文档

> 状态：设计阶段（待评审） · 适用：整个 `MultiClusterMgmtSys` 项目（认证/授权基础设施 + 登录页 + 角色权限）
> 本文档定义账号模型、登录流程、角色权限矩阵与接线方式，不给出具体实现代码。
> 认证 API 已对照 .NET 10 / ASP.NET Core 10 / Blazor Server 官方文档与源码核实（见 §10 来源）。

---

## 1. 设计目标与范围

### 1.1 设计目标

为多集群管理系统增加访问控制：打开应用时未登录用户先跳转到登录页，登录后按角色决定可执行的操作。

- **admin 账号**：登录后允许全部增删改查操作。
- **guest 账号**：登录后只允许查看（列表、详情、节点列表），不允许任何修改操作（添加/编辑/删除集群、刷新状态、新建/删除分组、查看连接密文）。

### 1.2 范围（本期纳入）

| 能力 | 说明 |
|---|---|
| 登录页 | 独立路由 `/login`，用户名 + 密码 + 记住我 |
| 首页跳转 | 未登录访问任意页 → 跳转 `/login`；登录后回跳原 URL |
| 角色权限 | admin / guest 两种角色，按操作粒度授权 |
| 账号持久化 | 账号存 SQLite，密码哈希存储；启动时种子 admin/guest 两个账号 |
| 登出 | AppBar 右侧登出按钮，清除 cookie 回到登录页 |
| 会话保持 | cookie 持久化（记住我）或会话级（不勾选） |

### 1.3 范围外（本期不做）

- 账号自助注册 / 改密 / 找回密码
- 多用户管理界面（增删账号、分配角色）
- 第三方登录（OAuth / OIDC）
- 细粒度资源级权限（如「只能看某分组」）
- 账号锁定 / 登录失败次数限制

> 上述能力已与需求方确认排除，可在后续迭代再加。本期账号仅 admin/guest 两个种子账号，如需新增账号临时通过手动改库或后续加管理界面。

## 2. 现状与差距

### 2.1 现有实现

- 无任何认证/授权：`Program.cs` 未注册 `AddAuthentication`/`AddAuthorization`，无 `UseAuthentication`/`UseAuthorization` 中间件。
- `Routes.razor` 用 `<Router>` + `<Found>` 直接渲染，无 `AuthorizeRouteView`。
- 所有页面（`/clusters`、`/clusters/{id}`）对匿名用户完全开放。
- 无账号模型、无登录页。

### 2.2 主要差距

| 差距 | 影响 |
|---|---|
| 无访问控制 | 任何人打开应用即可增删集群，凭据泄露风险 |
| 无登录页 | 无身份识别，无法区分 admin/guest |
| 无角色 | 无法做只读 vs 全权限的区分 |

## 3. 数据模型变更

> ⚠️ 本仓库无 EF 迁移，schema 由 `EnsureCreated()` 生成。新增 `Account` 表后需删除 `clusters.db*` 重建库（见 AGENTS.md）。

| 字段 | 类型 | 说明 |
|---|---|---|
| `Id` | `int` | 主键 |
| `Username` | `string` | 登录用户名，唯一、必填 |
| `PasswordHash` | `string` | 密码哈希（PBKDF2，见 §6.2），不存明文 |
| `Role` | `AppRole` | 角色：`Admin` / `Guest` |
| `CreatedAt` | `DateTime` | 创建时间 |

### 3.2 新增枚举 `AppRole`

```csharp
public enum AppRole { Admin, Guest }
```

### 3.3 `AppDbContext` 调整

- 新增 `DbSet<Account> Accounts => Set<Account>();`。
- `OnModelCreating` 中：`Account.Username` 设 `IsRequired()` + 唯一索引（`HasIndex(e => e.Username).IsUnique()`）；`PasswordHash` 设 `IsRequired()`。
- 无需调整现有 `ClusterGroup`/`ClusterInfo` 关系映射。

### 3.4 种子账号

启动时（`Program.cs` 中 `EnsureCreated()` 之后）检查并种子两个账号：

| 用户名 | 默认密码 | 角色 | 说明 |
|---|---|---|---|
| `admin` | `Changeme_123` | `Admin` | 全权限 |
| `guest` | `Changeme_123` | `Guest` | 只读 |

> 两个账号使用同一默认密码 `Changeme_123`，仅用于开发/内部工具首次启动。生产环境应在首次登录后改密（本期未做改密功能，文档中标注为后续迭代项）。种子逻辑：若 `Accounts` 表为空则插入两条；密码用 `PasswordHasher<string>` 哈希后存入。

## 4. 认证机制设计

### 4.1 技术选型：ASP.NET Core Cookie 认证

采用 ASP.NET Core 内置 cookie 认证（`CookieAuthenticationDefaults.AuthenticationScheme`），与 Blazor Server 交互式渲染兼容。理由：

- Blazor Server 交互式渲染时 `IHttpContextAccessor.HttpContext` 为 null（SignalR 电路事件不携带 HTTP 上下文），因此登录/登出**必须通过 HTTP 端点**（最小 API），不能在 Blazor 事件处理器里直接调 `SignInAsync`。
- cookie 由 `UseAuthentication` 中间件在建立 SignalR 连接的 HTTP 请求上读取，`ClaimsPrincipal` 经 `ComponentHub.StartCircuit` 注入到 `ServerAuthenticationStateProvider`，Blazor 电路内 `AuthorizeView`/`[Authorize]` 即可读取。
- 框架在 `MapRazorComponents` 时自动注册 `ServerAuthenticationStateProvider`，**无需自定义 `AuthenticationStateProvider`**。

### 4.2 服务注册（`Program.cs`）

```text
AddAuthentication(CookieAuthenticationDefaults.AuthenticationScheme)
    .AddCookie(options =>
    {
        options.Cookie.Name = "MultiClusterMgmtSys.Auth";
        options.Cookie.HttpOnly = true;
        options.Cookie.SameSite = SameSiteMode.Lax;
        options.ExpireTimeSpan = TimeSpan.FromHours(8);
        options.SlidingExpiration = true;
        options.LoginPath = "/login";
        options.LogoutPath = "/logout";
        options.AccessDeniedPath = "/access-denied";
    });
AddAuthorization();
AddCascadingAuthenticationState();   // 必须显式注册，AuthorizeRouteView 依赖它
AddHttpContextAccessor();            // 供 AccountService 等非 Blazor 服务使用
```

> `AddCascadingAuthenticationState()` **不被** `AddInteractiveServerComponents()` 自动调用，必须显式添加，否则 `AuthorizeRouteView`/`AuthorizeView` 拿不到级联 `AuthenticationState`。

### 4.3 中间件顺序

```text
UseHttpsRedirection → UseStaticFiles → UseAuthentication → UseAuthorization → UseAntiforgery → MapRazorComponents
```

`UseAuthentication`/`UseAuthorization` 必须在 `UseAntiforgery` 之前、`MapRazorComponents` 之前。它们只在建立 SignalR 连接的 HTTP 请求上生效（电路内 UI 事件走 SignalR，不经过中间件），但这是 cookie → 电路的必要桥梁。

### 4.4 登录/登出端点（最小 API）

在 `Program.cs` 注册两个 POST 端点（**不在 Blazor 组件里调 `SignInAsync`/`SignOutAsync`**）：

- `app.MapPost("/api/login", ...)`：接收 `{ username, password, rememberMe, returnUrl }`；调 `AccountService.ValidateCredentialsAsync` 校验；成功则构造 `ClaimsPrincipal`（`ClaimsIdentity` 的 `authenticationType` = `CookieAuthenticationDefaults.AuthenticationScheme`，claims 含 `ClaimTypes.Name` + `ClaimTypes.Role`），调 `HttpContext.SignInAsync(scheme, principal, props)`（`props.IsPersistent = rememberMe`）；返回 `200 OK`（含 `returnUrl`）或 `401 Unauthorized`。
- `app.MapPost("/api/logout", ...)`：调 `HttpContext.SignOutAsync(scheme)`；返回 `200 OK`。

> 登录端点返回 200/401 而非直接重定向——由前端 Blazor 组件根据响应做 `NavigationManager.NavigateTo(returnUrl, forceLoad: true)`。`forceLoad: true` **必需**：触发整页导航，销毁当前电路、重建带新 cookie 的电路，否则电路内 `AuthorizeView` 看不到新登录状态。

### 4.5 登录页与 Blazor 的交互

登录页 `Login.razor` 用 MudBlazor 组件（`MudForm`/`MudTextField`/`MudButton`）做表单与前端校验，提交时：

1. 用 `HttpClient`（注入 `IHttpClientFactory` 或直接 `HttpClient`）`PostAsJsonAsync("/api/login", payload)` 调登录端点。
2. 响应 200 → `NavigationManager.NavigateTo(returnUrl ?? "/clusters", forceLoad: true)`。
3. 响应 401 → `Snackbar.Add("用户名或密码错误", Severity.Error)`，不跳转。

> 此方案保留 MudBlazor 表单校验与样式，同时遵守「`SignInAsync` 只在 HTTP 端点调用」的约束。`HttpClient` 调本机端点在 Blazor Server（服务端）是安全的。

### 4.6 路由级保护（`Routes.razor`）

将 `<Router>` 内的 `<Found>` 内容从直接渲染改为 `AuthorizeRouteView`：

```text
<AuthorizeRouteView RouteData="@routeData" DefaultLayout="@typeof(MainLayout)">
    <NotAuthorized>
        @if (context.User.Identity?.IsAuthenticated == true)
        {
            <p>您没有权限访问该页面。</p>   @* 已登录但角色不足 *@
        }
        else
        {
            <RedirectToLogin />              @* 未登录 → 跳登录 *@
        }
    </NotAuthorized>
</AuthorizeRouteView>
```

`RedirectToLogin.razor`（新增辅助组件）：`OnInitialized` 中 `NavigationManager.NavigateTo($"/login?returnUrl={Uri.EscapeDataString(...)}", forceLoad: true)`。

> `[Authorize(Roles="Admin")]` 失败时**不会**触发 HTTP 302 到 `AccessDeniedPath`——Blazor 在电路内渲染 `<NotAuthorized>` 内容。因此「已登录但角色不足」的文案需在 `<NotAuthorized>` 里自行判断 `context.User.Identity?.IsAuthenticated` 区分两种情况。

### 4.7 页面级保护

- 所有需登录才能访问的页面在 `.razor` 顶部加 `@attribute [Authorize]`（`/clusters`、`/clusters/{Id:int}`）。
- 仅 admin 可访问的页面加 `@attribute [Authorize(Roles = "Admin")]`（本期无整页仅 admin 的页面；admin 限制通过组件内 `<AuthorizeView Roles="Admin">` 隐藏按钮实现，见 §5）。
- `/login` 页**不加** `[Authorize]`；但若已登录访问 `/login`，应在页面 `OnInitialized` 中 `NavigationManager.NavigateTo("/clusters")` 跳走。

### 4.8 组件内权限控制（`AuthorizeView`）

对「guest 不能操作」的按钮/入口，用 `<AuthorizeView Roles="Admin">` 包裹：

```text
<AuthorizeView Roles="Admin">
    <Authorized>
        <MudButton ...>添加集群</MudButton>
    </Authorized>
</AuthorizeView>
```

guest 登录时这些按钮不渲染（而非禁用——禁用仍可见，不够干净）。

### 4.9 登出

`MainLayout.razor` AppBar 右侧（主题切换按钮旁）加登出按钮，点击：

1. `HttpClient.PostAsync("/api/logout", ...)` 调登出端点（或直接 `NavigationManager.NavigateTo("/api/logout", forceLoad: true)` 用 GET 端点）。
2. 响应后 `NavigationManager.NavigateTo("/login", forceLoad: true)`。

> 同样需 `forceLoad: true` 销毁电路。登出按钮对 admin/guest 都可见（两种角色都能登出）。

## 5. 权限矩阵

| 操作 | admin | guest | 实现方式 |
|---|---|---|---|
| 查看集群列表（`/clusters`） | ✅ | ✅ | 页面 `@attribute [Authorize]`（两种角色均可） |
| 查看集群详情（`/clusters/{id}`） | ✅ | ✅ | 同上 |
| 查看节点列表（详情页实时拉取） | ✅ | ✅ | 只读 k8s 调用，不写库 |
| 显示连接密文（kubeconfig/token） | ✅ | ❌ | 详情页「显示密文」按钮包 `<AuthorizeView Roles="Admin">` |
| 添加集群 | ✅ | ❌ | 列表页「添加集群」按钮包 `<AuthorizeView Roles="Admin">` |
| 编辑集群 | ✅ | ❌ | 列表/详情「编辑」按钮包 `<AuthorizeView Roles="Admin">` |
| 删除集群 | ✅ | ❌ | 列表/详情「删除」按钮包 `<AuthorizeView Roles="Admin">` |
| 刷新集群状态 | ✅ | ❌ | 「刷新」按钮包 `<AuthorizeView Roles="Admin">`（刷新会写库：Status/Version/NodeCount/LastCheckedAt） |
| 新建分组 | ✅ | ❌ | 「新建分组」按钮包 `<AuthorizeView Roles="Admin">` |
| 删除分组 | ✅ | ❌ | 「分组管理」对话框内删除按钮包 `<AuthorizeView Roles="Admin">`；guest 可打开对话框查看但删除按钮不渲染 |
| 打开「分组管理」对话框 | ✅ | ✅（只看不删） | 对话框本身两种角色可打开 |
| 切换主题 | ✅ | ✅ | UI 偏好，不涉及数据 |
| 登出 | ✅ | ✅ | 两种角色都可登出 |

> 设计原则：guest 看到与 admin 相同的列表/详情，但所有「修改类」按钮不渲染。这样 guest 能完整浏览，只是无法改动。若希望 guest 连「分组管理」入口都看不到，可将该按钮也包 `<AuthorizeView Roles="Admin">`——本期保留入口可见、删除按钮隐藏，让 guest 能查看分组列表。

## 6. 服务层设计

### 6.1 `AccountService`（新增，`Services/AccountService.cs`）

| 方法 | 返回 | 说明 |
|---|---|---|
| `ValidateCredentialsAsync(string username, string password)` | `Task<Account?>` | 通过 `AccountRepository.GetByUsernameAsync` 取账号，用 `PasswordHasher` 校验密码；成功返回实体，失败返回 null |
| `CreateClaimsPrincipal(Account account)` | `ClaimsPrincipal` | 构造 `ClaimsIdentity`（`authenticationType` = cookie scheme，claims：`ClaimTypes.Name` = username、`ClaimTypes.Role` = role 名、`ClaimTypes.NameIdentifier` = Id）→ `ClaimsPrincipal` |
| `SeedAccountsAsync()` | `Task` | 启动时调用；若 `Accounts` 表为空，哈希默认密码后插入 admin/guest 两条 |

注入 `AccountRepository`、`PasswordHasher<string>`、`ILogger<AccountService>`。Scoped 生命周期。

### 6.2 密码哈希

用 `Microsoft.AspNetCore.Identity.PasswordHasher<TUser>`（BCL 自带，PBKDF2，无需额外 NuGet 包）：

- `PasswordHasher<string>`（`TUser` 用 `string` 即可，hasher 不实际使用该实例）。
- 哈希：`_hasher.HashPassword("", plainPassword)` → 存入 `PasswordHash`。
- 校验：`_hasher.VerifyHashedPassword("", storedHash, inputPassword)`，结果为 `Success` 或 `SuccessRehashNeeded` 视为通过，`Failed` 视为失败。

### 6.3 `AccountRepository`（新增，`Daos/AccountRepository.cs`）

| 方法 | 返回 | 说明 |
|---|---|---|
| `GetByUsernameAsync(string username)` | `Account?` | `db.Accounts.FirstOrDefaultAsync(a => a.Username == username)` |
| `CountAsync()` | `Task<int>` | 用于种子判断（表是否为空） |
| `AddAsync(Account entity)` | `Account` | 写入并返回 |

遵循 `项目结构设计.md` 硬约束：Repository 只返回实体，不感知 ViewModel、不调 k8s、不注入 UI 服务。

### 7.3 交互流程

1. 进入 `/login?returnUrl=...`，解析 `returnUrl`（默认 `/clusters`）。
2. 若已登录（`AuthorizeView` 已认证）→ 直接 `NavigateTo(returnUrl, forceLoad: true)`。
3. 填表 → 点登录 → `HttpClient.PostAsJsonAsync("/api/login", { username, password, rememberMe, returnUrl })`。
4. 200 → `NavigateTo(returnUrl, forceLoad: true)`。
5. 401 → 显示错误，清空密码框，不跳转。

### 7.4 路由

`@page "/login"`，`@layout null`（不套 MainLayout）。

## 8. 交互流程

### 8.1 首次访问（未登录）

```
打开应用 → 访问 /clusters（或任意页）
  → AuthorizeRouteView 检测未认证 → <NotAuthorized> → RedirectToLogin
  → 跳转 /login?returnUrl=/clusters（forceLoad）
  → 登录页加载
```

### 8.2 登录

```
/login 填表 → 提交 → POST /api/login
  → 校验通过 → SignInAsync 写 cookie → 返回 200
  → 前端 NavigateTo(returnUrl, forceLoad: true) → 整页刷新 → 新电路读 cookie → 已认证
  → 校验失败 → 返回 401 → 前端显示错误
```

### 8.3 guest 访问受限操作

```
guest 登录 → /clusters
  → 列表/详情正常渲染
  → 「添加集群」「编辑」「删除」「刷新」「新建分组」按钮不渲染（AuthorizeView Roles=Admin 隐藏）
  → guest 只能浏览
```

### 8.4 登出

```
点 AppBar 登出 → POST /api/logout → SignOutAsync 清 cookie → 返回 200
  → 前端 NavigateTo("/login", forceLoad: true) → 整页刷新 → 回登录页
```

## 10. 风险与注意事项

1. **模型变更须重建库**：新增 `Account` 表触发 schema 变更，必须删除 `clusters.db*` 重跑（无迁移，见 AGENTS.md）。建议与本次认证改动一并完成。
2. **`HttpContext` 在交互式 Blazor Server 中为 null**：登录/登出**必须**通过最小 API 端点（HTTP 请求）调 `SignInAsync`/`SignOutAsync`，**不能**在 Blazor `@onclick` 里直接调。登录后跳转必须 `forceLoad: true`，否则电路不重建、看不到新登录状态。
3. **默认密码风险**：admin/guest 默认密码均为 `Changeme_123`，仅适用开发/内部工具。生产环境需改密功能（本期未做，标注后续迭代）。文档与登录页可提示「首次登录后请修改密码」。
4. **cookie 安全**：`HttpOnly=true` 防 JS 读取；`SameSite=Lax`；生产 `SecurePolicy=Always`（需 HTTPS，本项目已启用 HTTPS 重定向）。会话 8 小时 + 滑动续期。
5. **`[Authorize(Roles="Admin")]` 不触发 302**：Blazor 在电路内渲染 `<NotAuthorized>`，需自行区分「未登录」vs「角色不足」。本期通过 `<AuthorizeView>` 隐藏按钮避免触发 `<NotAuthorized>`，整页 `[Authorize]` 仅用于「需登录」。
6. **`AddCascadingAuthenticationState` 易漏**：不被 `AddInteractiveServerComponents` 自动注册，必须显式调用，否则 `AuthorizeView`/`AuthorizeRouteView` 静默失效。
7. **guest 仍可调 API 端点**：本期只在 UI 层隐藏按钮，未在 Service/Repository 层做角色校验。若 guest 绕过 UI 直接调 `/api/login` 之外的端点……本期无其他写端点（写操作都走 Blazor 事件 → Service → Repository，不经过 HTTP 端点），所以 UI 隐藏已足够。后续若加 HTTP 写端点需在端点层加 `[Authorize(Roles="Admin")]`。
8. **种子账号幂等**：`SeedAccountsAsync` 仅在表为空时插入，重复启动不会重复插入、不会覆盖已改密码（本期无改密，但保留幂等习惯）。

## 12. 设计决策摘要

1. **Cookie 认证 + 最小 API 端点登录/登出**：Blazor Server 交互式渲染 `HttpContext` 为 null，登录/登出必须走 HTTP 端点；登录后 `forceLoad: true` 整页刷新重建电路。
2. **不写自定义 `AuthenticationStateProvider`**：框架自动注册 `ServerAuthenticationStateProvider`，cookie 经 `UseAuthentication` → `ComponentHub` → 电路注入，无需手写桥接。
3. **账号 DB 存储 + PBKDF2 哈希**：用 `PasswordHasher<string>`（BCL 自带），种子 admin/guest 两个账号。
4. **UI 层权限控制**：用 `<AuthorizeView Roles="Admin">` 隐藏修改类按钮，guest 看到完整列表/详情但无操作入口；整页 `[Authorize]` 仅做「需登录」门槛。
5. **登录页独立全屏**：不套 `MainLayout`，居中卡片，MudBlazor 组件 + `HttpClient` 提交最小 API 端点。
