## Why

The ConfigMap management pages (`/configmaps`, `/configmaps/{ClusterId}`, `/configmaps/{ClusterId}/{Namespace}/{Name}`, `/configmaps/{ClusterId}/{Namespace}/{Name}/{Name}/edit`, `/configmaps/{ClusterId}/{Namespace}/{Name}/yaml`) were written in the project's first-generation layout style (left TreeView cluster-picker + right self-contained content column, plus a parallel form-editor / YAML-editor pair) and have since been **commented out in place** (`@* ... *@` wrapping all five `.razor` files: `ConfigMaps.razor` 537 lines, `ConfigMapDetail.razor` 118 lines, `EditConfigMap.razor` 258 lines, `EditConfigMapYaml.razor` 152 lines, `CreateConfigMapDialog.razor` 168 lines of dead code). `Components/Layout/Drawer.razor:12` still links to `/configmaps`, so the dead pages are a live 404 path. The cluster/node features have since moved to a newer visual vocabulary (`MudPaper` toolbar + server/client-paged `MudTable` on list pages, `MudStack` of focused `MudCard`s on detail pages, established by `redesign-cluster-detail-with-endpoints`, `refactor-clusters-group-sidebar-layout`, and `redesign-nodes-page`). 

Beyond visual drift, the old design also carried a **semantic inconsistency**: a parallel form-editor path and YAML-editor path that were not equivalent (the form path silently dropped `binaryData`, never showed `labels`/`annotations`, and reused an inline hand-rolled `MudOverlay` dialog for "add key"). The redesign collapses the feature to a single **"YAML-first" mental model** — read = only-read YAML view, edit = YAML submit, create = YAML submit — bringing the page back online in the current visual vocabulary while eliminating the form/YAML parity bug.
